# AGENTS.md — working on the uroboros testbed

This repository measures the [uroboros](https://github.com/NicolasET/uroboros) plugin; its value is that the measurement stays the same from one uroboros version to the next. The rules and process of the uroboros repository's own AGENTS.md apply here too (interview the maintainer before changing behavior, plan approval, coherence sweep, no Claude commit trailers, talk to the maintainer in Spanish).

## Invariants

1. **The scenario is fixed.** `scenario/idea.md`, `scenario/truth.md`, `scenario/standing-decisions.md`, `scenario/hidden-tests/`, `fixture/` and the oracle's rules (`harness/oracle.ts`) define what is measured. Never change them silently. A change needs the maintainer's approval and a bump of `SCENARIO_VERSION` in `harness/config.ts`; results of different scenario versions are never compared. `scenario/verify/` defines the verifier eval (`verify` mode) apart: a change there, or to its scoring, bumps `VERIFY_EVAL_VERSION` instead, and the `verify` row is compared only within one eval version, whatever the scenario version; a change to `fixture/` bumps it too, since its workspaces copy the fixture. `scenario/review/` and the reviewer eval's scoring work the same way with `REVIEW_EVAL_VERSION`, and `scenario/implement/` and the implement eval's prompt and measures with `IMPLEMENT_EVAL_VERSION`. The reviewer eval's step-B prompt (`stepBPrompt`) follows each uroboros version's protocol: supporting a new version extends it without changing an earlier version's prompt, and needs no bump.
2. **The fixture decides none of the planted ambiguities.** No code in `fixture/` may settle who pauses, visibility, ordering, rank preservation or idempotency — otherwise uroboros has nothing to ask. A standing decision (`scenario/standing-decisions.md`) may touch one only when the idea contradicts it, so it still reaches the user.
3. **uroboros never sees the answers.** The hidden tests, the truth files and the reference implementations (`harness/reference/`, `scenario/implement/reference/`) stay out of every workspace until the run ends. The `verify` and `review` workspaces are the exception by design: those modes measure the verifier and the reviewer, not ambiguity detection, so their product is the reference implementation with a planted defect, under a fixed spec.
4. **Pinned graders.** The oracle and judge models are exact model ids. The role model follows the latest Opus at its own default effort, and every result records the exact model and effort.
5. **Isolated sessions.** Sessions load project settings only (`settingSources: ['project']`, for the fixture's spec-kit skills), in workspaces outside the user's home with no `CLAUDE.md`, `AGENTS.md` or `.claude` above them (`assertIsolatedRoot`), and every tool call outside the workspace, the plugin and the session's temporary directory is denied (`harness/sandbox.ts`). Nothing from the machine running the testbed may influence a result.
6. **Results are data.** Never edit a committed `results/` file by hand; re-run instead.

## Verifying a change to the harness

- `npm run typecheck` and `npm test` (the hidden tests must fail 11/11 on the bare fixture and pass 11/11 on `harness/reference/`, with a green gate; the runtime tests must fail 3/3 on the bare fixture and pass 3/3 on the reference; every verifier eval case must pass the hidden tests 11/11 in process with a green gate, while a probe of its running server shows its defect, and nothing on the clean copy; every reviewer eval case must keep the gate green with its defect in place, and its clean copy pass the hidden tests 11/11; the implement eval's hidden tests must fail 14/14 on the workspace a run resumes, whose gate is green, and pass 14/14 on `scenario/implement/reference/` with a green gate, and its `tasks.md` must give each user story only its own two files).
- After a change to how a session runs, run one mode for real (`--modes compat` is the shortest) before a full run.
